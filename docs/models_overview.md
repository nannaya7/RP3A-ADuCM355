### 0.05 센서 어레이 (사용자 확인, 2026-10-24)

> **키트의 센서는 3개가 어레이로 구성되어 있고, 한 번 측정할 때 3개 센서를 모두 읽는다.**

펌웨어와의 대응:
- 3개 센서 = 채널 **CH0, CH1, CH2** (펌웨어 기본 채널 마스크 `0x7`, CH3은 미사용). `CHAN CH0,CH1,CH2` → `START 1` **한 번**이 센서 3개를 순서대로 한 번씩 스윕한다 (CH0 → CH1 → CH2, **순차 측정**; 동시 측정은 하드웨어상 불가).
- 센서마다 곡선(10Hz~200kHz, 101점)이 하나씩 나오므로, **한 번의 측정 = 3개 곡선**이다.
- 펌웨어는 **채널별로 RTIA 자동 레인지 테이블과 SHORT 보정**을 따로 가진다 → 센서마다 임피던스가 달라도 문제 없다.

**해석(확인 필요)**: Troponin 코드가 단계마다 요구하는 "3회 반복 파일"(T1×3, T2×3, T3×3, c0×3)은 **센서 3개가 만든 3개 곡선**일 가능성이 크다. 그렇다면:

| 해석 | 단계당 `START` | 단계당 곡선 | T1/T2/T3 합계 |
|---|---|---|---|
| **A. 센서 3개 = 코드의 3반복** (유력) | **1회** (`START 1`) | 3 | 곡선 9개 |
| B. 센서 3개 × 시간 반복 3회 | 3회 | 9 | 곡선 27개 (측정 시간 3배) |

- 코드는 T2에서 **반복 중 일부를 QC로 제외**(RMS>0.08, 최소 2개 유지)하는데, 이는 **센서 하나가 불량이어도 나머지 2개로 계산**하는 어레이 설계와 맞는다.
- 해석 A이면 앞서 정리한 "단계마다 3회 측정"은 "단계마다 **1회 측정(센서 3개)**"으로 바뀌고 총 시간이 크게 줄어든다.
- **확인 요청**: 센서 3개는 같은 항목의 반복(replicate)인가? 단계마다 시간 반복도 더 하는가? NT-proBNP 키트도 같은 3센서 구조인가?

UI 영향: 단계 화면에 **센서 3개의 상태**(대기/측정 중/완료/SAT·불량)를 따로 보여 주고, 센서별 진행률과 단계 전체 진행률(채널 3개 × 101점)을 표시한다. 센서 하나가 불량이면 코드의 QC 규칙대로 제외하고 계속할지, 재측정할지 정책이 필요하다 (T1/T3의 평균에는 QC가 없다는 점에 유의).

**단계 이름 정리 (사용자 설명, 2026-10-24)**: 사용자는 단계를 **T0, T1, T2**라고 부르며, **각 단계에서 센서 0, 1, 2를 순서대로 읽는다.**

| 사용자 단계 | 센서 읽기 | 우리가 이해한 의미 (**추정, 확인 필요**) | Troponin 코드의 이름 |
|---|---|---|---|
| **T0** | 센서 0 → 1 → 2 | 혈액 투입 전 기준 측정(빈 센서) | `T1` (redox probe, 혈액 전) |
| **T1** | 센서 0 → 1 → 2 | 혈액 투입, 15분 반응 후 측정 | `T2` (혈액 15분 반응 후) |
| **T2** | 센서 0 → 1 → 2 | 세척 후 기준 용액 측정 | `T3` (세척 후 redox probe) |

- 이 문서의 이전 부분(§0.1 표, §4.1 등)이 쓰는 **T1/T2/T3는 Troponin 코드의 이름**이다. UI에는 사용자가 쓰는 **T0/T1/T2**를 표시하되, 내부 처리(모델 입력)는 위 표로 대응시킨다.
- 이 대응이 맞는지 확인이 필요하다. 다르면 표만 고치면 된다.
- 단계마다 센서 3개를 읽는 것은 펌웨어의 한 사이클(`START 1`)과 같으므로 **단계당 `START` 1회**가 된다 (해석 A).

## 2. 공통 사실
- 둘 다 **임피던스 스펙트럼(EIS)** 에서 농도를 추정한다. 펌웨어는 `FREQ_HZ / MAG_OHM / PHASE_DEG / R_OHM / X_OHM`을 점마다 제공하므로 **원료 데이터는 충분**하다.
- 둘 다 **연구용·임시 모델**이며 코드에 임상 검증 주장이 없다. GUI는 결과에 **"연구용(비검증)"** 표기와 모델 버전을 항상 함께 보여준다.
- 둘 다 **QC(범위 검사)** 가 있고, QC 실패 시 숫자를 억제하거나(Troponin) 경고를 붙인다(NT-proBNP).
- 둘 다 신뢰할 수 없는 입력이면 결과를 믿지 않도록 **재측정 경로**가 필요하다.

## 4. 측정·진단 흐름 수정안

### 4.1 Troponin — 다단계 프로토콜
```
[배치 시작: 시각 기록] → (선택) c0 기준 측정
STEP T1: redox probe 3회 ─ 안내 "혈액 도포" ─ 15분 타이머 ─ STEP T2: 3회
 ─ 안내 "세척" ─ STEP T3: 3회  ─ (c0 기준 T2 3회: 같은 배치)
→ 계산(D, B) → QC → 농도 / 재측정
```
- 각 STEP = `START 1` **1회**(센서 3개 = CH0~CH2가 한 사이클에 측정됨, 해석 A — §0.05) → `CYCLE=1 done` 확인. 시간 반복이 더 필요하면(해석 B) `START 1`을 3회
- 단계 사이에 **사용자 확인/대기** 화면, T2의 15분 타이머, 중단 후 복구 정책이 필요하다.
- 곡선 수: 해석 A에서 단계당 3개(센서 3개), 합계 9개 (+c0 3개). 한 사이클 시간은 센서 1개 스윕(수십 초~1분 이상 추정) × 3 → 단계당 **수 분 이내**, 여기에 T2 전 대기 15분이 추가된다 (실기 측정으로 확정).

### 4.2 NT-proBNP — 확정 전
- 측정 단계 수와 `delta_Rct`의 기준(전/후?)이 정해져야 흐름을 확정할 수 있다.
- 특징 추출 코드를 받은 뒤, **그 코드가 요구하는 입력(몇 단계, 어떤 주파수점)** 에 맞춰 설계한다.

### 4.2.1 단계 진행 규칙 — 사용자 수락 게이트 (확정 요구사항)

> **각 단계(1→2→3)는 측정을 마친 뒤 사용자가 다음 진행을 수락할 때까지 대기한다. 수락 후에만 다음 단계를 시작한다.** 자동으로 넘어가지 않는다.

```
[단계 1 측정 3회] → 단계 1 완료 화면 (요약·QC) ─ [다음 단계] 수락 대기
        ↓ 수락
[단계 2 측정 3회] → 단계 2 완료 화면 ───────── [다음 단계] 수락 대기
        ↓ 수락
[단계 3 측정 3회] → 단계 3 완료 → 계산 → 결과
```

| 규칙 | 내용 |
|---|---|
| 단계 완료 조건 | 해당 단계의 3회 반복이 모두 끝나고 QC 통과(또는 사용자가 재측정 선택) |
| 수락 전 | 다음 단계 `START`를 **절대 보내지 않는다.** 모듈은 유휴(`RUN=0`) 유지 |
| 수락 화면 | 단계 요약(반복 수, 경고, SAT 여부), 다음 단계에 필요한 사용자 작업 안내(예: 혈액 도포, 세척), `[다음 단계]` / `[이 단계 재측정]` / `[중단]` |
| 재측정 | 단계 단위로 다시 측정 가능(이전 단계 결과는 유지). 재측정 횟수 제한은 미정 |
| 대기 중 연결 | 대기 중에도 UART 연결 상태를 감시. 모듈 재시작(부팅 배너) 시 현재 단계 무효 처리하고 안내 |
| 유휴 시간 | 모든 단계(T1/T2/T3)에서 **타이머와 프로그레스 바**를 표시한다. **T2 전 15분 반응 대기**는 타이머가 끝나면 버튼이 활성화되고 사용자가 클릭해야 T2가 시작된다 (**최소 대기 강제 + 수동 시작**). 그 외 단계 사이 수락 버튼은 별도 대기 없이 활성 |
| 중단/복구 | 단계별 완료 결과를 **즉시 임시 저장**해 앱이 꺼져도 직전 단계까지 복구 가능하게 한다 (정책 미정) |
| 모델 의존 | 단계 수·내용은 `Assay.protocol()`이 정한다. Troponin은 T1/T2/T3(+c0), NT-proBNP는 미정 |

> 이 규칙은 "단계 1 = T1, 단계 2 = T2, 단계 3 = T3"라는 해석에 기반한다. 맞는지 확인이 필요하다.

**진행 방식 결정 (2026-10-24 사용자 확정, 담당자와 재협의 예정)**
- 현재: **수동 시작.** 타이머가 끝나도 **자동으로 넘어가지 않고** 사용자가 버튼을 눌러야 한다. 단, **T2 전 15분 대기는 끝나기 전까지 버튼이 비활성**이다 (2026-10-24 정리에서 변경).
- 보류: 담당자와 상의해 **자동 진행**(타이머 종료 시 자동 시작) 또는 **최소 대기 강제**로 바꿀지 다시 확정한다.
- 구조: 나중에 바꾸기 쉽도록 단계 정의에 진행 정책을 둔다 — `Confirm(mode="manual" | "auto_after_wait" | "manual_after_min_wait", wait_s=...)`. T2 전 대기는 `manual_after_min_wait`(wait_s=900), 그 외 기본 `manual`.
- 타이머 완료 시: 시각/소리 알림(예: 화면 강조)만 하고 상태는 바꾸지 않는다. (사용자가 확정하지 않은 세부 UX는 구현 시 최소로)

### 4.3 공통 구조 제안
```python
class Assay(Protocol):             # 검사 항목 하나(NT-proBNP / Troponin)
    name: str; model_version: str
    def protocol(self) -> list[Step]: ...      # 단계(측정/대기/안내)와 스윕 설정
    def diagnose(self, data: AssayData) -> DiagnosisResult: ...
```
- `Step`: `Measure(preset, repeats=3)`, `Wait(seconds)`, `Prompt(message)`, **`Confirm(message)`**(사용자 수락 게이트 — 모든 `Measure` 뒤에 기본 삽입, §4.2.1)
- 화면은 `Assay.protocol()`을 순서대로 실행하는 **일반 단계 실행기**로 만들면 두 모델과 향후 모델을 같은 UI로 처리할 수 있다.
- `DiagnosisResult`에는 `value`, `unit`, `qc_pass`, `warnings`, `model_version`, `research_use_only=True`를 담는다.
