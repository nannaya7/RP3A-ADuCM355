# 설정 화면 — Wi-Fi / 블루투스

2026-10-25 추가. 가로(1280x800)와 세로(480x800) 모두 같은 기능이다.

## 1. 화면과 동작
- **설정 버튼**: 로그인 화면과 측정 화면의 **우측 상단**에 톱니바퀴 버튼. 누르면 설정 화면이 열리고, `← 뒤로`를 누르면 **열기 전에 보던 화면**(로그인 또는 측정)으로 돌아간다.
  - 측정 중에 열어도 측정은 계속된다 (화면만 바뀌고 컨트롤러는 그대로).
  - 설정 화면과, 터치 키보드가 열려 있을 때는 버튼을 숨긴다 (입력란과 겹침 방지).
  - 위치: 가로 (오른쪽 36, 위 26, 48px) / 세로 (오른쪽 12, 위 12, 44px). `app/app_window.py`의 `GEAR_LANDSCAPE`, `GEAR_PORTRAIT`.
  - 가로 측정 화면은 모듈 문구가 버튼과 겹치지 않게 오른쪽에 64px 비워 두었다.
- **탭**: `Wi-Fi` / `블루투스`. 처음 열 때(탭이 처음 보일 때) 자동으로 한 번 읽고, 그 뒤에는 `검색`으로 갱신한다.
- 구성: 위쪽 상태 줄(연결 상태, `켜기/끄기`, `검색`) → 목록(가로는 왼쪽, 세로는 위) → 상세 카드(가로는 오른쪽, 세로는 아래).
- 목록 줄: 이름, 부제(보안·신호 / MAC), 배지(`연결됨`/`저장됨`/`등록됨`), 신호 막대. 손가락으로 밀어서 스크롤.
- 터치 키보드: 비밀번호 입력란을 누르면 키보드가 열리고, 위쪽 요소(탭, 상태 줄, 세로는 목록까지)를 접어 입력란과 버튼이 키보드 위에 남는다.

### Wi-Fi
| 동작 | 설명 |
|---|---|
| 검색 | 주변 네트워크를 다시 찾는다 (3~5초). 같은 이름은 신호가 센 것 하나만, `연결됨 > 저장됨 > 신호 순` |
| 연결 | 새 보안 네트워크는 비밀번호(8자 이상)를 입력해 연결. **연결에 성공하면 자동 저장(= 등록)** 되어 다음부터는 비밀번호 없이 연결된다 |
| 연결 해제 / 저장 삭제 | 연결된 항목은 `연결 해제`, 저장된 항목은 `저장 삭제` |
| 직접 입력 | 목록에 안 보이는(숨겨진) 네트워크의 이름과 비밀번호를 입력해 연결 |
| 켜기/끄기 | Wi-Fi 전원 (`nmcli radio wifi`) |
- 비밀번호를 틀리면 반쯤 만들어진 저장 정보를 지우고 "비밀번호가 맞지 않습니다."를 보여 준다. 입력한 글자는 남겨 둔다.
- 이미 저장된 네트워크에 새 비밀번호를 넣으면 옛 정보를 지우고 다시 만든다.

### 블루투스
| 동작 | 설명 |
|---|---|
| 검색 | 약 8초간 주변 장치를 찾는다 (`bluetoothctl --timeout 8 scan on`). 이름이 없는 장치는 "이름 없는 장치"로 아래쪽에 |
| 등록 | **페어링 + 신뢰(trust) + 연결**. 신뢰한 장치는 다음부터 자동 연결. 페어링은 최대 30초 |
| 연결 / 연결 해제 | 등록된 장치 |
| 등록 삭제 | `bluetoothctl remove` |
| 켜기/끄기 | 켜기 전에 `rfkill unblock bluetooth` 도 한다 |
- **한계**: PIN 입력이나 숫자 확인이 필요한 장치(키보드, 일부 단말)는 지원하지 않는다. `NoInputNoOutput` 에이전트로 'Just Works' 방식만 한다 (프린터, 스캐너, 스피커, 센서류는 대개 가능). 필요하면 PIN/확인 대화상자를 추가한다.
- **켜기 실패 `org.bluez.Error.Busy`** (Pi 실기에서 확인된 오류): 직전 전원 요청이나 컨트롤러 초기화가 아직 끝나지 않았을 때 나온다. 앱은 1초 간격으로 최대 12번(약 12초) 다시 시도하고, 그 사이에 이미 켜졌으면 성공으로 본다. 그래도 안 되면 원인(rfkill 차단, bluetooth 서비스 꺼짐, 장치 없음/`disable-bt`)을 찾아 해결 명령과 함께 화면에 보여 준다. `tools/net_check.py` 는 블루투스가 안 켜질 때 진단 출력(rfkill, 서비스 상태, hciconfig, dmesg)을 한꺼번에 보여 준다.
- Pi 3A+ 는 Wi-Fi 와 블루투스가 한 칩을 나눠 쓰므로 검색 중에 Wi-Fi 속도가 잠깐 느려질 수 있다.
- **UART 와의 관계**: 이 프로젝트는 모듈 통신에 `/dev/serial0`(미니 UART)을 쓰므로 블루투스(PL011)와 충돌하지 않는다. `pi_setup.sh --disable-bt` 를 쓰면 블루투스가 꺼져 이 화면의 블루투스는 쓸 수 없다.

## 2. 구조
```
net/
  runner.py     외부 명령 실행 (명령 없음=127, 시간 초과=124 를 예외 대신 rc 로)
  wifi.py       NmcliWifi (nmcli) / MockWifi          — 출력 해석 parse_wifi_list, parse_saved, split_terse
  bluetooth.py  BluetoothctlBackend / MockBluetooth    — parse_devices, parse_info, pair_session
  tasks.py      TaskRunner: 블로킹 호출을 백그라운드에서 실행하고 결과를 GUI 스레드로 전달 (한 번에 하나)
  errors.py     NetError (사용자에게 보여 줄 한국어 문구)
ui/
  gear_button.py    설정 버튼 (직접 그림, SVG 플러그인 불필요)
  settings_page.py  SettingsPage → WifiPanel / BluetoothPanel (공통 DevicePanel)
```
- 화면은 백엔드 메서드만 부른다: Wi-Fi `radio/set_radio/scan/current/connect/disconnect/forget`, 블루투스 `powered/set_power/devices/scan/register/connect/disconnect/remove`.
- 백엔드는 `runner`(와 `pairer`)를 주입받아 시험에서 가짜로 바꾼다 (`tests/test_net.py`).
- 가상 백엔드: Windows 이거나 `--mock` 이거나 `config.ini [network] mock = true` 일 때. 가상 Wi-Fi 는 비밀번호 `12345678` 이 맞는 것으로 처리하고, 가상 블루투스는 `...:04` 장치가 페어링을 거절한다.

## 3. 설정
`config.ini`
```ini
[network]
mock = false      ; true: 가상 백엔드 (PC 시험용. Windows 는 자동)
```
(Pi 의 `config.ini` 는 덮어쓰지 말고, 필요하면 위 두 줄만 추가한다. 없어도 기본값 false 로 동작한다.)

## 4. Pi 에 필요한 것
- 패키지: `network-manager`, `bluez`, `rfkill` (`deploy/pi_setup.sh` 의 apt 단계가 설치하고 사용자를 `bluetooth` 그룹에 넣는다 → 다시 로그인).
- Trixie 데스크톱은 NetworkManager 가 기본이다. `nmcli` 로 저장한 접속 정보는 재부팅 후에도 유지된다.
- 앱은 **데스크톱에 로그인한 사용자**로 실행해야 한다. SSH 에서 `sudo` 없이 실행하면 polkit 권한 때문에 Wi-Fi 변경이 "권한이 없습니다"로 거부될 수 있다 (VNC 터미널이나 자동 시작에서는 정상).
- 비밀번호는 `nmcli` 인자로 전달되므로 연결하는 순간에 `ps` 로 보일 수 있다 (키트 내부 사용이라 허용했다).

## 5-1. 센서 탭 (패치 센서 / 내장 센서, 2026-10-26)
설정 화면의 세 번째 탭 **`센서`**. ADuCM355 모듈을 어느 경로로 쓸지 고른다. **동시에 하나만** 켜진다.
| 센서 | 연결 | 토글 |
|---|---|---|
| 패치 센서 | 블루투스로 ADuCM355 연결 | ON 이 되면 내장 센서는 자동 OFF |
| 내장 센서 | UART 로 ADuCM355 연결 (`config.ini [uart] port`, 기본 `/dev/serial0`) | ON 이 되면 패치 센서는 자동 OFF |
- 켜진 센서를 다시 누르면 **둘 다 OFF** (연결 안 함). 각 카드에 `꺼짐` / `연결됨 · …` / `연결 중… 연결 안 됨 · 이유` 가 보인다.
- 선택은 `data/sensor.json` 에 저장되어 **재시작해도 유지**된다. 처음에는 `config.ini [sensor] default` (기본 `builtin` = 내장 센서, 이전과 같은 동작).
- **패치 센서를 켤 때는 실제로 연결해 모듈에 조회(`STATUS`)를 보내 응답을 확인한다.** 토글을 누르면 패치 센서 연결(블루투스 직렬 포트)로 바꾸고 "패치 센서에 연결하고 모듈을 확인하는 중…"을 보이며, 컨트롤러의 모듈 확인(`STATUS` → `CALSTATUS` → `ENV`)이 끝나기를 기다린다 (최대 8초, `AppWindow.probe_timeout_s`).
  - 모듈이 응답하면(READY) 켜진 것으로 **저장**한다.
  - 포트가 안 열리거나 모듈이 응답하지 않으면(NO_MODULE / 시간 초과) **이전 센서로 되돌리고**(저장도 바뀌지 않음) 팝업 **"먼저 센서를 연결해 주세요."** 를 보인다. 그동안 토글은 잠기고, 되돌린 뒤 다시 시도할 수 있다.
  - 검사가 끝난(DONE/ERROR) 상태에서는 모듈 확인이 저절로 다시 돌지 않아, 확인을 위해 컨트롤러를 `처음부터` 상태로 되돌린다.
  - 블루투스 연결 여부를 따로 묻지 않고 모듈의 실제 응답으로 판단하므로, 포트/전원/페어링 어느 쪽 문제든 같은 팝업이 뜬다. 내장 센서를 켜거나 끌 때는 이 확인이 없다.
- **패치 센서로 검사하는 중에는 블루투스 `검색`을 막는다.** 검색(약 8초)이 이미 연결된 센서의 통신을 느리게 하거나 끊을 수 있어서(Pi 3A+ 는 Wi-Fi 와 블루투스가 같은 칩·안테나를 나눠 쓴다), 패치 센서가 켜져 있고 검사가 진행 중이거나 센서를 확인하는 중이면 `검색` 버튼과 블루투스 탭을 처음 열 때의 자동 검색 모두 하지 않는다 ("패치 센서를 사용하는 중에는 블루투스 검색을 할 수 없습니다. 검사가 끝난 뒤에 검색해 주세요." 표시, 이미 아는 장치 목록만 읽는다). 내장 센서일 때, 패치 센서여도 검사 전이거나 끝난 뒤에는 검색할 수 있다. (5GHz Wi-Fi 를 쓰면 간섭이 더 줄어든다.)
- **검사 중에는 바꿀 수 없다** (측정 중이거나 1단계 이상 진행 중이고 아직 끝나지 않음): 다른 센서의 값이 섞이지 않게 거절하고 안내 문구를 띄운다. 검사를 끝내거나 측정 화면의 `처음부터` 후에 바꾼다.
- 전환하면 UART 워커가 이전 연결을 닫고 새 장치로 다시 연결한다 (`UartWorker.set_transport`). 측정 컨트롤러는 연결이 바뀐 것을 보고 모듈 확인(STATUS)을 다시 한다. 모니터링 화면에는 어느 경로로 오가든 같은 로그가 쌓인다.
- 코드: `comm/sensor.py`(선택 규칙·저장·장치 생성), `ui/sensor_panel.py`(토글 카드), `comm/uart_worker.py`(`set_transport`), `app/app_window.py`(`_on_sensor_mode`). 시험: `tests/test_sensor.py` (12개).

### 패치 센서의 블루투스 연결 — BLE (Nordic UART Service)
패치 센서의 ADuCM355 는 **BLE Nordic NUS 로 UART 를 그대로 흉내** 낸다. 패킷 처리는 유선 UART 와 완전히 같고, 바이트를 주고받는 계층만 BLE 다 (`comm/ble_transport.py`, `bleak`).
```ini
[sensor]
default = builtin             ; builtin | patch | off  (처음 실행할 때만. 이후는 data/sensor.json)
patch_name = nFor           ; 광고 이름이 이 글자로 시작하는 장치 (펌웨어 DEVICE_NAME 예: "nFor30-001", 버전마다 숫자가 다르다)
patch_address =               ; 비우면 이름/NUS 서비스로 검색, 지정하면 그 주소로만 연결
```
- 장치 찾기: 광고 이름이 `patch_name` 으로 시작하거나 NUS 서비스(6E400001-…)를 광고하는 장치. 주소를 적으면 그 주소만.
- 패치 센서가 **여러 대**이면 설정 > 센서 > "패치 센서 선택"에서 [검색] 후 하나를 고른다. 고른 장치의 주소는 `data/sensor.json` 에 저장되고 `patch_address` 보다 우선한다. 고르지 않으면 처음 발견된 `nFor…` 장치에 연결되므로 여러 대일 때는 꼭 고른다. 이미 연결된 센서는 광고하지 않아 검색되지 않는다.
- `nFor` 접두사는 **패치 센서 연결에만** 쓴다. 설정 > 블루투스 탭의 검색은 이름 제한 없이 모든 장치를 보여 준다(키보드·마우스 등 연결용, 필터는 사용자가 입력할 때만).
- 쓰기는 RX 특성(6E400002)에 MTU 크기로 쪼개 보내고, 읽기는 TX 특성(6E400003)의 notify 를 모은다.
- 패치 센서 ON: 검색 → 연결 → STATUS 확인까지 최대 약 20초(`probe_timeout_s`) 기다린다. 못 찾으면 이전 센서로 되돌리고 "먼저 센서를 연결해 주세요." 팝업.
- 링크가 끊기면 워커가 다시 검색·연결을 시도한다. Pi 에는 `python3-bleak` 이 필요하다 (`pi_setup.sh` 가 설치).
- **Pi 실기 미확인**: 검색 시간, 연결 시간, 패킷 쪼개짐/속도(101점 × 3센서 수신)를 실제 모듈로 확인해야 한다.

## 6. Pi 에서 확인할 것
**먼저 실제 명령으로 점검 도구를 돌린다** (`tools/net_check.py`). 화면과 같은 `net/` 백엔드로 진짜 `nmcli`/`bluetoothctl` 를 실행해, 원본 출력과 앱이 해석한 결과를 나란히 보여 주고 형식이 가정과 다르면 `!!` 로 알린다.
```bash
cd ~/PyNFor
python3 tools/net_check.py --save ~/pi_net.txt          # 읽기만 (아무것도 바꾸지 않음)
python3 tools/net_check.py --bt-scan                    # 블루투스 8초 검색 포함
python3 tools/net_check.py --connect "SSID" --password "비밀번호"   # (바꿈) 실제 연결
python3 tools/net_check.py --bt-register AA:BB:CC:DD:EE:FF          # (바꿈) 실제 페어링
```
`--save` 파일(명령과 원본 출력)과 `!!` 항목을 보내 주면 해석을 바로 고친다. 실제 출력이 확보되면 그대로 `tests/fixtures/` 에 넣어 시험을 실제 출력 기반으로 바꾼다.

그 다음 화면에서:
1. `nmcli -t -f IN-USE,SSID,SIGNAL,SECURITY device wifi list` 출력이 화면 목록과 같은지.
2. 새 네트워크 연결 → 재부팅 후 자동 연결되는지. 비밀번호 오류 문구.
3. 숨은 네트워크(직접 입력) 연결.
4. 블루투스: 검색 목록, Just Works 장치 등록(페어링 응답이 바로 오는지, `pair_session` 의 30초 제한), 자동 재연결.
5. 키보드가 열렸을 때 입력란/버튼 위치 (특히 세로).
6. 목록을 손가락으로 밀 때 스크롤과 탭(선택)이 모두 되는지 (`QScroller` 사용).
